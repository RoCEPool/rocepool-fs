# rocepool 執行手冊

rocepool 是以 RDMA/RoCE 記憶體池為基礎的分散式檔案系統，組成如下：

- 以原生 C 撰寫的 MDT（中繼資料）伺服器與 OST（資料）伺服器
- 三種用戶端：C 的 FUSE 用戶端、LD_PRELOAD 攔截函式庫、Python 參考實作
- OST 可掛載的 NVMe 容量層（核心 O_DIRECT 或 SPDK 後端，P2PDMA 為選用）
- 全套自動化：預檢、編譯、部署、啟動服務、執行官方 IO500、產生附瓶頸分析的報告

本手冊只說明「怎麼執行」。各輪的設計與結果請見 `README.md` 和 `docs/`（最新一輪：`docs/AWS_ROUND.md`）。

**最省事的入口**：

- 解壓縮後執行 `sudo ./run.sh`。有 RDMA 網卡就在實機上執行，沒有就以 10 節點模擬執行。
- 在 AWS 上：`python3 tools/aws_cluster.py run ...`（第 4b 節）。

## 1. 目錄結構

| 目錄 | 內容 |
|---|---|
| `roce/native/` | C 程式碼。主要檔案：`roce_transport.c`（RDMA 傳輸，以 verbs/rdma_cm 支援 RoCE 網卡與 Soft-RoCE）、`ofi_transport.c`（相同介面的 libfabric 傳輸，供 AWS EFA 使用）、`rocepool_servers.c`（MDT/OST 伺服器）、`ost_tier.c`（OST 的 NVMe 容量層）、`rocepool_fs.c`（用戶端核心）、`rocepool_fuse.c`（FUSE 用戶端）、`rocepool_intercept.c`（LD_PRELOAD 攔截用戶端）、`rocepool_kv.c`（原生 KV API）、`rocepool_cufile.c`（GPU 直讀，cuFile 介面）、`build.sh`（實體網卡用的編譯）、`softverbs/`（RDMA 使用者空間模擬器，沒有網卡時使用） |
| `roce/`, `fs/`, `storage_engine/` | Python 參考實作（協定、MDT、資料分條、POSIX 層） |
| `tools/` | 自動化工具：`roce_onsite.py`（實機一條指令完成）、`io500_run.py`（N 節點 IO500）、`bench_ior.py`（本機 IOR/mdtest）、`roce_preflight.py`（RoCE 預檢）、`nvme_preflight.py`（NVMe/P2P 預檢）、`io500_model.py`（瓶頸分析與預測）、`aws_cluster.py`（AWS 一條指令：開機 → 建置環境 → 執行 → 取回報告 → 釋放）、`bench_gds.py`（GPU 檢查與直讀測速）、`bench_kvcache.py`（KV cache 重複使用與 TTFT） |
| `tests/` | 465 個測試（`python3 -m unittest discover -s tests -t .`） |
| `stress_reports/` | 歷次執行報告（JSON）。編號即時間順序，最新為 `39_io500_sim10_intercept.json` |
| `docs/` | 各輪的設計文件與結果 |

## 2. 所需環境

**可離線使用。** 套件中的 `deps/` 收錄了所有第三方原始碼。

- 收錄內容：MPICH 4.2.3、官方 IO500（含固定版本的 IOR、pfind、lz4、schema 工具）、IOR、libfabric 2.1.0、rdma-core 59.2。
- IOR 已預先產生 configure，現場不需要 autotools 也不需要外部網路。編譯時會自動從這裡取用（`tools/deps.py`）。
- 設定 `ROCEPOOL_OFFLINE=1` 會完全禁止從網路下載。缺少東西時不會卡在下載，而是立即顯示缺什麼。
- FUSE 用戶端不依賴系統核心標頭的版本，因此在 Ubuntu 22.04（核心 5.15）上也能編譯。
- 要更新這些原始碼時，請在能連上網際網路的機器上執行 `tools/make_deps.sh`。

**每台機器**（部署到實機時，所有節點都必須符合）：

- Linux x86_64，核心 5.x 以上。FUSE over io_uring 需要 6.14 以上，P2PDMA 需要 6.2 以上。
- root 權限（用於掛載 FUSE、命名空間、修改 RoCE 參數）。
- `python3` 3.9 以上、`gcc`、`make`、`git`、`cmake`（自動編譯 rdma-core 時使用）。
- 實體網卡：rdma-core 開發套件（`libibverbs-dev librdmacm-dev` / `rdma-core-devel`）。`build.sh` 會自行安裝，或從原始碼編譯。
- 執行 IO500 的機器另外需要 `curl` 與 `autoconf automake libtool pkg-config`。MPICH 與 IOR/IO500 會在第一次執行時自動下載、編譯並放在 `.bench_cache/`，之後重複使用。
- 多台機器時：
  - 從本機能以無密碼 ssh 登入各節點（`root@host`）。
  - 主機名稱全部不同。
  - 程式碼樹在**所有機器上的絕對路徑相同**（指令碼會自動同步）。

**沒有網卡的開發機**：除了 rdma-core 之外符合上述條件即可。測試與模擬叢集全部以 `softverbs` 模擬器執行。

## 4. 部署到實機並執行 IO500（主要流程）

**一條指令完成全部。** 流程如下：

1. 預檢、編譯、驗證傳輸層
2. 同步到各節點，在各節點預檢與編譯
3. 啟動 N 個 MDT、N 個 OST
4. 探測用戶端
5. 執行官方 IO500
6. 產生報告、清理

### 4.0 叢集設定檔 cluster.conf（建議使用，台數無上限）

把所有節點寫進一個檔案後，只要在其中任一台執行 `sudo ./run.sh` 就會一路跑完。不需要 `--peers`，也不會詢問密碼。

```bash
cp cluster.conf.example cluster.conf     # 之後編輯它
sudo ./run.sh                            # 有 cluster.conf 就照它執行；其他檔案用 --conf 指定
```

```
[login]
# 各節點上具有 sudo 權限的使用者及其密碼（所有節點相同）
# 注意：password 那一行後面不要寫註解，# 也會被當成密碼的一部分
user = admin
password = xxxx
[nodes]
# SSH 位址      RoCE IP            主機名稱（選填）
10.0.0.11       10.10.0.11      node01
10.0.0.12      10.10.0.12     node02
...                                   # 100 台就寫 100 行
```

run.sh 會自動完成下列事項（`tools/cluster_conf.py`，每 32 台並行）：

1. 依 RoCE IP 判斷哪一行是本機，其餘全部視為對端節點。本機的 RoCE IP 同時作為 `--ip`。
2. 建立本機 root 到各對端節點的無密碼登入。
   - 已經能無密碼登入的節點不做任何事。
   - 無法登入的節點，以 `[login]` 的使用者與密碼**只登入一次**，把本機 root 的公鑰加到對端的 root。不需要 sshpass，也不需要人工輸入。
   - 之後的執行不再使用密碼。
3. 主機名稱重複時（複製出來的機器常見），改為第 3 欄的名稱。沒有重複就不更改。
4. 這個檔案含有密碼，因此會自動改為只有 root 能讀取（600）。它不會被打包進程式套件，也不會同步到其他節點。公鑰設定完成後，可以刪除密碼。

密碼為空、且節點間還不能無密碼登入時，會在終端機詢問一次（所有節點共用）。

### 4.1 直接以命令列參數指定

```bash
# 1 台（網卡迴路）
sudo python3 tools/roce_onsite.py --ip 192.168.50.1

# 2 台
sudo python3 tools/roce_onsite.py --ip 192.168.50.1 --peer root@node2 --peer-ip 192.168.50.2

# N 台（10 節點）：在 --peers 中以 user@host=RoCE_IP 列出本機以外的各節點
sudo python3 tools/roce_onsite.py --ip 192.168.50.1 \
     --peers root@n2=192.168.50.2,root@n3=192.168.50.3,...,root@n10=192.168.50.10 \
     --bench full
```

參數：

| 參數 | 意義 |
|---|---|
| `--ip` | 本機的 RoCE IP（省略時從 RoCE v2 的 GID 自動偵測） |
| `--peers` | 其他節點，`user@host=ip` 以逗號分隔 |
| `--bench quick\|full\|none` | `quick`（預設）：30 秒 stonewall 的短程執行。`full`：短程執行後接著**不做任何修改的官方 300 秒正式執行**（可提交的分數）。`none`：只部署，不執行 |
| `--force` | 某個步驟 FAIL 也繼續 |
| `--lib` | 略過編譯，使用現有的函式庫 |
| `--report` | 報告路徑（預設 `onsite_report.json`） |

每個步驟輸出 PASS / WARN / FAIL，預設在第一個 FAIL 時停止。預檢會自動修正能修正的項目（RoCE v2 模式、memlock 限制、主機名稱解析），無法修正的則顯示原因。

**輸出檔案**：

| 檔案 | 內容 |
|---|---|
| `onsite_report.json` | 各步驟的結果與細節 |
| `onsite_io500.json` | 短程執行的 IO500 報告（含瓶頸分析與預測） |
| `onsite_io500_valid.json` | `--bench full` 正式執行的報告 |
| `onsite_cluster.json` | 叢集描述。之後可用 `ROCEPOOL_CLUSTER=onsite_cluster.json python3 tools/io500_run.py ...` 以任意組態重新執行 |
| `roce_env.sh` | 預檢決定的傳輸參數（ToS/DSCP、busy-poll 等） |
| `.bench_cache/io500_run/` | 原始輸出：`io500.out`、各伺服器的日誌 `mdt<節點>_<埠>.log` / `ost<節點>_<埠>.log`、用戶端日誌、IO500 的 `results/` |

**執行中自動決定的事項**（不需要手動操作）：

1. **用戶端**：分別以下列 3 種做短程執行，採用最快的一種。3 個結果都在報告的 `client_probe` 中，正式執行沿用短程執行的選擇。
   - FUSE 一般通道
   - FUSE over io_uring（核心支援時自動啟用 `fuse.enable_uring`）
   - LD_PRELOAD 攔截函式庫
2. **NVMe 層**：在各節點執行 `tools/nvme_preflight.py`。
   - NVMe 上有檔案系統時，OST 的資料直寫（write-through）到那裡。每個 OST 一個檔案，大小依可用空間自動決定。
   - 沒有時只使用記憶體。
   - 各節點的判斷記錄在報告的 `ost_tier` 欄位。
   - 原始區塊裝置與 SPDK **不會自動選用**（見第 6 節）。
3. **P2P 記憶體**：下列條件全部成立時，OST 的請求緩衝區從磁碟的 CMB 配置：
   - 核心 6.2 以上
   - 網卡為 mlx5
   - 磁碟公開 CMB
   - 網卡與磁碟位於同一個 root port 之下

   網卡拒絕註冊時會自動改回主機記憶體，並在 OST 日誌記錄一行。

## 4b. 在 AWS 上執行

EC2 沒有 RoCE 網卡，因此有兩種方法。兩種都以**一條指令**完成全部。

請先在本機安裝 `aws` CLI 並登入。所需權限如下：

- EC2：建立與刪除執行個體、安全群組、金鑰對、置放群組
- SSM：讀取公開參數

```bash
# 方法 2：EFA（AWS 自家的 RDMA 網卡，硬體 RDMA read）。libfabric 傳輸後端；build.sh 偵測到 EFA 時自動選用
python3 tools/aws_cluster.py run --mode efa --nodes 10 --region us-east-1

# 方法 1：Soft-RoCE（rxe）。程式碼不變，由核心把一般網卡變成 RoCE v2 裝置。由 CPU 代替網卡處理，因此量到的是軟體效能
python3 tools/aws_cluster.py run --mode rxe --nodes 3 --quick

python3 tools/aws_cluster.py list                       # 仍在使用資源的執行
python3 tools/aws_cluster.py down --run-id rp-2026...   # 釋放（使用 --keep 或中斷之後）
```

自動執行的內容：

1. 確認憑證與區域。
2. 選擇 Ubuntu 24.04 映像，以及該機型可用的可用區域。
3. 建立金鑰對、安全群組、cluster 置放群組。
   - 安全群組允許成員之間的所有流量（EFA 必需）。
   - SSH 只允許來自本機公用 IP 的連線。
4. 啟動 N 台（efa 模式下每台附一張 EFA 網卡）。
   - **每台到達 `--max-hours`（預設 6 小時）會自動關機並終止。** 即使與本機的連線中斷，也不會持續計費。
5. 建置各台的環境，並設定節點間 root 的無密碼登入。
   - rxe：載入 `rdma_rxe`，執行 `rdma link add rxe0`，把 MTU 設為 9001。
   - efa：安裝 AWS 的 EFA 安裝程式（含 libfabric）。
6. 把程式碼樹傳到第 1 台，在那裡執行 `./run.sh --peers <其他各台的私有 IP>`。進度即時顯示。
   - 內容包括預檢、編譯、傳輸驗證、功能測試、效能測試、全節點 IO500。
7. 把報告取回到 `aws_runs/<run-id>/`。
8. 終止執行個體，刪除建立的所有資源（加上 `--keep` 則保留）。

| 參數 | 意義 |
|---|---|
| `--mode efa\|rxe` | 傳輸方式（預設 efa） |
| `--nodes` | 台數（預設 10） |
| `--type` | 執行個體類型。efa 預設 `c6in.32xlarge`（128 vCPU、200 Gb、支援 RDMA read 的 EFA），rxe 預設 `c6in.16xlarge`。需要本機 NVMe 時用 `i4i.32xlarge`。efa 模式必須使用支援 EFA 的機型（不支援時當場拒絕，不會啟動） |
| `--quick` | 30 秒短程執行（不加時，短程執行後接著官方 300 秒正式執行） |
| `--max-hours` | 安全上限（預設 6） |
| `--keep` | 執行後不釋放，並顯示 ssh 指令 |
| `--self-test` | 在主節點也執行單元測試 |
| `--az` / `--region` / `--ssh-cidr` / `--disk-gib` | 可用區域、區域、允許 SSH 的網段、系統磁碟 |

已經自行啟動 AWS 機器時：

- **支援 EFA 的機型**：安裝 EFA 安裝程式後直接執行 `sudo ./run.sh --peers ...`。會自動辨識 EFA 並使用 libfabric 後端。
- **一般機型**：`sudo ./run.sh --soft-roce --peers ...`。在各台自動建立 rxe0。
- 兩者都必須在安全群組中允許成員之間的所有流量。

兩種方法的差異：

- **rxe**：所有 RDMA 操作都由 CPU 處理，頻寬與延遲遠不及實體網卡。適合驗證功能與多節點流程。
- **EFA**：真正的 RDMA（SRD 可靠資料包，Nitro v4 以上機型具硬體 RDMA read）。分數有意義。
- EFA 不保證送達順序，因此做了下列處理：
  - 單邊讀取的驗證配合亂序設計（先讀資料，後讀版本號）。
  - 單邊中繼資料查詢在 EFA 上預設關閉（需要 3 次往返，比 1 次 RPC 慢）。可用 `ROCEPOOL_DIRECT_LOOKUP=1` 強制開啟。

詳見 `docs/AWS_ROUND.md`。

## 4c. GPU 直讀（GPUDirect Storage）

大量使用 GPU 的程式（例如算圖或訓練）可以把 rocepool 的資料直接送進 GPU 記憶體。

- 網卡把 OST 記憶體上的資料以 RDMA 直接寫入 GPU 記憶體，不經過主機記憶體，CPU 不碰資料（與 Vendor W、DDN 的 GDS 支援相同）。
- 介面是 NVIDIA 標準的 cuFile（`libcufile.so.0`）。PyTorch/KvikIO、RAPIDS、DALI，以及用 cuFile 讀資料的算圖器，都不必修改程式碼。

```bash
# 在 GPU 節點上（build.sh 已編譯 roce/native/cufile/libcufile.so.0）
export LD_LIBRARY_PATH=<rocepool 目錄>/roce/native/cufile:$LD_LIBRARY_PATH
export ROCEPOOL_MDTS=... ROCEPOOL_OSTS=...      # 與攔截函式庫相同
export ROCEPOOL_PREFIX=/mnt/rocepool            # FUSE 掛載點（或攔截函式庫的前綴）
python3 你的程式                                 # 它的 cuFile 讀寫直接在 rocepool 與 GPU 記憶體之間流動
```

- **不需要任何手動操作。** `run.sh` 有 `gds` 步驟（結果在 `onsite_gds.json`，包含在結果套件中）。
  - 對每台機器確認下列事項：
    - GPU 與驅動程式。
    - GPU 記憶體能否註冊到網卡。dma-buf 需要開源版的核心模組；也可以使用 nvidia-peermem，不足時會自動 modprobe。
    - PCIe 上 GPU 與網卡的距離。位於不同 CPU 插槽時會顯示提醒。
  - 有 GPU 的機器也會測速，各以 GB/s 輸出：
    - 直接到 GPU 記憶體。
    - 經由主機記憶體。不支援 GDS 的儲存就是這樣。
    - 所有 GPU 同時讀取。
- 沒有 GPU 的機器，這個步驟顯示 "no NVIDIA GPU"，不算失敗。
- GPU 記憶體無法註冊時，自動改為經由主機記憶體。結果仍然正確，報告會標上 WARN。
- **AI 推論的 KV cache（前綴快取、prefill/decode 分離）**：KV API 新增了直接與 GPU 記憶體交換資料的呼叫，適合 KV 區塊。
  - 在 Python 中的用法：
    - `buf = kv.register_device(tensor.data_ptr(), 位元組數)`
    - `kv.cached_prefix(區塊鍵的清單)`：每個 OST 1 次往返，查出已快取的前綴區塊數。
    - `buf.mget(...)` / `buf.mput(...)`
  - 資料由網卡直接以 RDMA 進出 GPU 記憶體，不經過主機記憶體，也不經過中繼資料伺服器。
  - `run.sh` 的 `kvcache` 步驟會自動測量：
    - 使用實際模型的 KV 大小：quick 為 Llama-3-8B、4096 個 token 中快取 3072 個；full 為 Llama-3-70B、8192 個 token 中快取 6144 個。
    - 寫入、前綴查詢、讀進 GPU 記憶體，並逐區塊驗證資料。
    - 輸出：讀取延遲（p50/p99）、GB/s、TTFT。TTFT 比較使用快取與全部重新計算兩種情況。prefill 時間依 GPU 型號的算力估算，報告中會註明。
    - 結果在 `onsite_kvcache.json`。沒有 GPU 的機器只測「讀進主機記憶體」這一段。
- 詳見 `docs/GPUDIRECT_STORAGE.md`。

```
phase            measured   emu%  rpc/op  hot MDT   projected   bottleneck
ior-easy-write   ...        ...                                 RAM to hold a 300 s write phase / NVMe tier write bandwidth
mdtest-hard-write ...                                           per-rank latency / CPU of the busiest node / ...
projected on ...: bw X GiB/s, md Y kIOPS, score Z
score range over the estimated inputs: a .. b
vs Vendor W (score 105.94): ...
what the fixes are worth (cumulative): ...
```

- **measured**：這次實際跑出的數值。在實機上這就是你的分數（正式執行請看 `[SCORE]` 那一行）。
- **bottleneck**：依實測的每次操作 CPU / RPC / 位元組數推估，該階段最先碰到的上限。
- **projected**：把實測的每次成本套用到目標硬體的預測（`--project`，實機預設為 `auto`，即該主機本身）。
  - 在實機上，實測與預測應該幾乎一致。差距很大時，代表模型漏掉了什麼。
  - 比率顯示在表中的 "model check" 那一行。
- 實機的報告中，`node_facts`、`ost_tier`、`client_probe`、`fuse_channel_probe`、`dead_servers`（伺服器當掉時附上日誌結尾）也值得一看。

## 6. 手動控制（選用）

`roce_onsite.py` 建好叢集（`onsite_cluster.json`）之後，可以直接呼叫 `io500_run.py`。

```bash
export ROCEPOOL_CLUSTER=onsite_cluster.json
sudo -E python3 tools/io500_run.py --valid                      # 官方 300 秒正式執行
sudo -E python3 tools/io500_run.py --client intercept --ost-tier none   # 強制使用攔截函式庫 + 只用記憶體
sudo -E python3 tools/io500_run.py --ost-tier file:/dev/nvme1n1 # 各節點相同的原始磁碟（會被覆寫！）
sudo -E python3 tools/io500_run.py --ost-tier spdk:0000:41:00.0 # SPDK 後端（需以 SPDK_DIR 編譯，見下文）
```

常用參數：

| 參數 | 意義 |
|---|---|
| `--client auto\|fuse\|intercept` | 使用的用戶端 |
| `--direct-read auto\|on\|off` | 單邊讀取與單邊查詢。auto 以探測比較開與關後決定 |
| `--bind-ranks auto\|numa\|core\|none` | rank 的綁定方式 |
| `--fuse-uring auto\|on\|off` | FUSE over io_uring |
| `--ost-tier auto\|none\|file:PATH[:GIB]\|spdk:TRADDR[:NSID]` | OST 的容量層。`{n}` 代表 OST 的編號 |
| `--ost-ram-cache-mib` | OST 的 RAM 快取 |
| `--ranks-per-node`、`--mdts-per-node`、`--osts-per-node` | 每節點的 rank 數、MDT 數、OST 數 |
| `--stonewall`、`--valid`、`--project`、`--report` | stonewall 時間、正式執行、預測目標、報告路徑 |

**SPDK 後端**的步驟（每台機器都要做）：

1. 編譯 SPDK：`git clone https://github.com/spdk/spdk && cd spdk && git submodule update --init && ./configure && make`。
2. 把目標 NVMe 綁定到 vfio-pci（`scripts/setup.sh`）。該磁碟會脫離核心。
3. 執行 `SPDK_DIR=/path/to/spdk bash roce/native/build.sh`。
4. 指定 `--ost-tier spdk:<PCI 位址>` 執行。

SPDK 路徑已確認能以 v25.05 的標頭編譯，但尚未在硬體上執行過。第一次請檢查 OST 日誌。

**只執行本機效能測試**（1 台，使用 2 個網路命名空間或實體網卡）：

```bash
sudo python3 tools/bench_ior.py --backend dist --hard                      # FUSE 用戶端
sudo python3 tools/bench_ior.py --backend dist --hard --client intercept   # 攔截函式庫
sudo python3 tools/io500_run.py --nodes 10                                 # 在本機完整模擬 10 個節點
```

**只用攔截函式庫執行任意程式**：

```bash
LD_PRELOAD=roce/native/librocepool_intercept.so ROCEPOOL_PREFIX=/mnt/rocepool \
ROCEPOOL_MDTS=h1:19901,h2:19901 ROCEPOOL_OSTS=h1:19951,h2:19951 \
mpirun -n 32 ior -a POSIX -o /mnt/rocepool/f ...
```

`/mnt/rocepool` 不需要真的存在。它只是一個前綴，其他路徑照原樣交給 libc。

## 8. 常見問題

| 症狀 | 處理方式 |
|---|---|
| 預檢 FAIL：RoCE 模式 / memlock | 以 root 執行的預檢會自動修正。無法修正時，會顯示具體的 sysfs/configfs 路徑 |
| 主機名稱相同，或解析到 127.x | 指令碼會自動寫入 `/etc/hosts` 修正。仍然失敗時，請依顯示內容手動加上那一行 |
| "IO500 did not start in 300 s" | MPI 的 rank 之間連不上。請確認 ssh 無密碼登入、防火牆、主機名稱解析 |
| 伺服器當掉（`dead_servers`） | 請查看對應的 `ost<節點>_<埠>.log` / `mdt<節點>_<埠>.log`，以及報告中的 `kernel_log`（OOM 等）。記憶體不足時請調整 `--mem-budget-gib` |
| 用戶端 RPC 逾時（`timed out waiting for completion`） | 機器嚴重過載時會發生。請加大 `ROCEPOOL_RPC_TIMEOUT_MS` |
| OST 日誌出現 `ibv_reg_mr refused the supplied (P2P) chunk memory` | 網卡驅動程式不支援註冊 P2P 頁面。已自動改回主機記憶體，不影響功能 |
| `Write phase needed ...s instead of stonewall 300s`（ior-easy 為 INVALID） | 資料塞不進 300 秒。卡在哪個 OST 的容量，寫在執行開頭 `IOR data budget ... from the OSTs' capacity` 那一行。NVMe（含 LVM/RAID 上的）檔案系統會自動成為容量層；沒有時使用本機最大的本地檔案系統。不會自動寫入原始磁碟，需要時請指定 `--ost-tier file:/dev/nvmeXnY` |
| 執行中伺服器當掉 | IO500 立即停止，不執行剩下的階段。報告的 `dead_servers[].kernel_log` 附有該機器的核心日誌（OOM 等） |
| NVMe 層寫入失敗 `tier full` | 容量層檔案太小。請以 `--ost-tier file:PATH:GIB` 指定更大的值 |
| AWS：`has no EFA` | 該機型不支援 EFA。請改用 `c6in.32xlarge` / `i4i.32xlarge` / `hpc7a.96xlarge` 等，或使用 `--mode rxe` |
| AWS：預檢 `libfabric` FAIL | EFA 安裝程式沒有正確安裝，或安全群組沒有允許成員之間的所有流量 |
| AWS：預檢 `rdma_read` WARN | 機型不是 Nitro v4 以上。RDMA read 由 libfabric 在對端 CPU 上模擬。功能正常，但單邊讀取較慢。探測會自動在單邊讀取與 RPC 讀取之間選擇 |
| AWS：無法建立 rxe | 核心沒有 `rdma_rxe`。請執行 `apt install linux-modules-extra-$(uname -r)` |
| AWS：中途斷線 | 機器會在 `--max-hours` 自動終止。也可以用 `aws_cluster.py down --run-id ...` 立即釋放 |

## 9. 本輪結果摘要（詳見 `docs/KERNEL_BYPASS_ROUND.md`）

- **攔截函式庫與 FUSE 的比較**（2 核模擬器，ior-hard）：攔截函式庫寫入快 1.9 倍、讀取快 2.6 倍、create 快 1.5 倍。
- **10 節點模擬**（`stress_reports/39`）：
  - 實測 1.68 → 3.02。
  - 對 10 × 32 核 / 100 GbE 的預測為 375（只用記憶體）/ 687（NVMe 層）。Vendor W 為 105.94。
  - 中繼資料的預測是上限值，頻寬取決於實際磁碟的寫入頻寬。
- **相同硬體（96 核 / 750 GB / 200G）的預測**：806 / 1 342。逐項比較記錄在開發時的討論中。
- **單邊讀取／查詢 + NUMA 綁定**（`docs/ONE_SIDED_ROUND.md`、`stress_reports/41`）：
  - 10 節點模擬實測 3.02 → 3.77。
  - stat 階段快 2.5～3 倍，預測 375 → 449。
- **AWS**（`docs/AWS_ROUND.md`）：
  - 新增 EFA 傳輸後端（libfabric），所有測試在兩種後端上都通過。
  - 以 `tools/aws_cluster.py` 一條指令即可啟動叢集並執行 IO500。
