# rocepool 実行マニュアル

rocepool は、RDMA/RoCE を使ったメモリプール型の分散ファイルシステムです。構成は次のとおりです。

- ネイティブ C で書いた MDT（メタデータ）サーバーと OST（データ）サーバー
- 3 種類のクライアント：C の FUSE クライアント、LD_PRELOAD インターセプトライブラリ、Python のリファレンス実装
- OST に付けられる NVMe 容量層（カーネルの O_DIRECT または SPDK バックエンド、P2PDMA はオプション）
- 一通りの自動化：事前チェック、ビルド、デプロイ、サービス起動、公式 IO500 の実行、ボトルネック分析付きのレポート作成

このマニュアルは「どう動かすか」だけを扱います。各ラウンドの設計と結果は `README.md` と `docs/` を参照してください（最新ラウンドは `docs/AWS_ROUND.md`）。

**いちばん手軽な入口**：

- 展開して `sudo ./run.sh`。RDMA NIC があれば実機で、なければ 10 ノードのシミュレーションで動きます。
- AWS では `python3 tools/aws_cluster.py run ...`（4b 節）。

> 中国語版：[运行说明书.md](运行说明书.md)（内容は同じです）。

| `tests/` | 465 個のテスト（`python3 -m unittest discover -s tests -t .`） |

| `docs/` | 各ラウンドの設計ドキュメントと結果 |

## 2. 必要な環境

**オフラインで使えます。** パッケージの `deps/` にサードパーティのソースがすべて入っています。

- 収録しているもの：MPICH 4.2.3、公式 IO500（固定バージョンの IOR、pfind、lz4、schema ツールを含む）、IOR、libfabric 2.1.0、rdma-core 59.2。
- IOR は configure 生成済みなので、現地で autotools も外部ネットワークも要りません。ビルド時に自動でここから取り出します（`tools/deps.py`）。
- `ROCEPOOL_OFFLINE=1` を設定すると、ネットワークからのダウンロードを完全に禁止します。足りないものがあれば、ダウンロードで止まらずに何が足りないかをすぐ表示します。
- FUSE クライアントはシステムのカーネルヘッダーのバージョンに依存しないので、Ubuntu 22.04（カーネル 5.15）でもビルドできます。
- これらのソースを更新するときは、インターネットにつながるマシンで `tools/make_deps.sh` を実行します。

**各マシン**（実機にデプロイするときは全ノードが満たす必要があります）：

- Linux x86_64、カーネル 5.x 以上。FUSE over io_uring には 6.14 以上、P2PDMA には 6.2 以上が必要です。
- root 権限（FUSE のマウント、名前空間、RoCE パラメーターの修正に使います）。
- `python3` 3.9 以上、`gcc`、`make`、`git`、`cmake`（rdma-core を自動ビルドするときに使います）。
- 実 NIC の場合：rdma-core の開発パッケージ（`libibverbs-dev librdmacm-dev` / `rdma-core-devel`）。`build.sh` が自分でインストールするか、ソースからビルドします。
- IO500 を実行するマシンには、さらに `curl` と `autoconf automake libtool pkg-config` が必要です。MPICH と IOR/IO500 は初回実行時に自動でダウンロード・ビルドされて `.bench_cache/` に置かれ、以降は再利用されます。
- 複数マシンの場合：
  - このマシンから各ノードへパスワードなしで ssh できること（`root@host`）。
  - ホスト名がすべて異なること。
  - コードツリーが**全マシンで同じ絶対パス**にあること（スクリプトが自動で同期します）。

**NIC のない開発マシン**：上記から rdma-core を除けば足ります。テストとシミュレーションクラスターはすべて `softverbs` エミュレーターで動きます。

## 4. 実機へのデプロイと IO500（メインの手順）

**コマンド 1 つですべて完了します。** 流れは次のとおりです。

1. 事前チェック、ビルド、転送層の検証
2. 各ノードへの同期、各ノードでの事前チェックとビルド
3. MDT を N 個、OST を N 個起動
4. クライアントのプローブ
5. 公式 IO500 の実行
6. レポート作成、後片付け

### 4.0 クラスター設定ファイル cluster.conf（推奨、台数の上限なし）

全ノードを 1 つのファイルに書いておけば、そのうちどれか 1 台で `sudo ./run.sh` を実行するだけで最後まで進みます。`--peers` は不要で、パスワードを聞かれることもありません。

```bash
cp cluster.conf.example cluster.conf     # その後、編集する
sudo ./run.sh                            # cluster.conf があればそれに従う。別のファイルは --conf で指定
```

```
[login]
# 各ノードで sudo 権限を持つユーザーとそのパスワード（全ノード共通）
# 注意：password の行の後ろにコメントを書かないこと。# もパスワードの一部になります
user = admin
password = xxxx
[nodes]
# SSH アドレス      RoCE IP            ホスト名（任意）
10.0.0.11       10.10.0.11      node01
10.0.0.12      10.10.0.12     node02
...                                   # 100 台なら 100 行
```

run.sh は次のことを自動で行います（`tools/cluster_conf.py`、32 台ずつ並列）。

1. RoCE IP でどの行が自分自身かを判別し、残りをすべて相手側ノードとします。自分の RoCE IP は `--ip` としても使われます。
2. このマシンの root から各相手ノードへのパスワードなしログインを整えます。
   - すでにパスワードなしで入れるノードには何もしません。
   - 入れないノードには `[login]` のユーザーとパスワードで**一度だけ**ログインし、このマシンの root の公開鍵を相手の root に登録します。sshpass も人の入力も要りません。
   - 以降の実行ではパスワードは使いません。
3. ホスト名が重複している場合（クローンしたマシンでよくあります）は、3 列目の名前に変更します。重複していなければ変更しません。
4. このファイルはパスワードを含むので、自動で root だけが読める権限（600）に変更します。プログラムのパッケージには含まれず、他のノードにも同期されません。公開鍵の登録が済んだら、パスワードは消してかまいません。

パスワードが空で、ノード間でまだパスワードなしログインができない場合は、ターミナルで一度だけ聞かれます（全ノード共通）。

### 4.1 コマンドライン引数で直接指定する

```bash
# 1 台（NIC のループバック）
sudo python3 tools/roce_onsite.py --ip 192.168.50.1

# 2 台
sudo python3 tools/roce_onsite.py --ip 192.168.50.1 --peer root@node2 --peer-ip 192.168.50.2

# N 台（10 ノード）：--peers に自分以外の各ノードを user@host=RoCE_IP 形式で並べる
sudo python3 tools/roce_onsite.py --ip 192.168.50.1 \
     --peers root@n2=192.168.50.2,root@n3=192.168.50.3,...,root@n10=192.168.50.10 \
     --bench full
```

引数：

| 引数 | 意味 |
|---|---|
| `--ip` | このマシンの RoCE IP（省略すると RoCE v2 の GID から自動検出） |
| `--peers` | 他のノード。`user@host=ip` をカンマ区切りで |
| `--bench quick\|full\|none` | `quick`（デフォルト）：30 秒 stonewall の短時間実行。`full`：短時間実行のあとに**手を加えない公式の 300 秒本番実行**（提出可能なスコア）。`none`：デプロイだけして実行しない |
| `--force` | どこかのステップが FAIL でも続行 |
| `--lib` | ビルドを省略し、既存のライブラリを使う |
| `--report` | レポートのパス（デフォルト `onsite_report.json`） |

各ステップは PASS / WARN / FAIL を出力し、デフォルトでは最初の FAIL で止まります。事前チェックは直せるもの（RoCE v2 モード、memlock の制限、ホスト名の解決）を自動で修正し、直せないものは理由を表示します。

**出力ファイル**：

| ファイル | 内容 |
|---|---|
| `onsite_report.json` | 各ステップの結果と詳細 |
| `onsite_io500.json` | 短時間実行の IO500 レポート（ボトルネック分析と予測を含む） |
| `onsite_io500_valid.json` | `--bench full` の本番実行のレポート |
| `onsite_cluster.json` | クラスターの記述。あとで `ROCEPOOL_CLUSTER=onsite_cluster.json python3 tools/io500_run.py ...` として任意の構成で再実行できます |
| `roce_env.sh` | 事前チェックで決まった転送パラメーター（ToS/DSCP、busy-poll など） |
| `.bench_cache/io500_run/` | 生の出力。`io500.out`、各サーバーのログ `mdt<ノード>_<ポート>.log` / `ost<ノード>_<ポート>.log`、クライアントのログ、IO500 の `results/` |

**実行中に自動で決まること**（手作業は不要です）：

1. **クライアント**：次の 3 つをそれぞれ短時間実行し、いちばん速いものを使います。3 つの結果はすべてレポートの `client_probe` にあり、本番実行も短時間実行の選択をそのまま使います。
   - FUSE の通常チャネル
   - FUSE over io_uring（カーネルが対応していれば `fuse.enable_uring` を自動で有効化）
   - LD_PRELOAD インターセプトライブラリ
2. **NVMe 層**：各ノードで `tools/nvme_preflight.py` を実行します。
   - NVMe 上にファイルシステムがあれば、OST のデータをそこへライトスルーします。OST ごとに 1 ファイルで、サイズは空き容量から自動で決めます。
   - なければメモリだけで動きます。
   - 各ノードの判断はレポートの `ost_tier` フィールドに記録されます。
   - 生のブロックデバイスと SPDK は**自動では選びません**（6 節を参照）。
3. **P2P メモリ**：次の条件がすべてそろうと、OST のリクエストバッファーをディスクの CMB から割り当てます。
   - カーネル 6.2 以上
   - NIC が mlx5
   - ディスクが CMB を公開している
   - NIC とディスクが同じ root port の下にある

   NIC が登録を拒否した場合は自動でホストメモリに戻り、OST のログに 1 行記録されます。

## 4b. AWS で実行する

EC2 には RoCE NIC がないので、方法は 2 つあります。どちらも**コマンド 1 つ**で全部行います。

事前に、このマシンに `aws` CLI をインストールしてログインしておいてください。必要な権限は次のとおりです。

- EC2：インスタンス、セキュリティグループ、キーペア、プレイスメントグループの作成と削除
- SSM：パブリックパラメーターの読み取り

```bash
# 方法 2：EFA（AWS 独自の RDMA NIC、ハードウェアの RDMA read）。libfabric 転送バックエンド。build.sh は EFA を見つけると自動で選択
python3 tools/aws_cluster.py run --mode efa --nodes 10 --region us-east-1

# 方法 1：Soft-RoCE（rxe）。コードは変えず、カーネルが通常の NIC を RoCE v2 デバイスにする。NIC の代わりに CPU が処理するので、測れるのはソフトウェア
python3 tools/aws_cluster.py run --mode rxe --nodes 3 --quick

python3 tools/aws_cluster.py list                       # まだリソースを使っている実行
python3 tools/aws_cluster.py down --run-id rp-2026...   # 解放（--keep 使用時や中断後に）
```

自動で行う内容：

1. 認証情報とリージョンを確認する。
2. Ubuntu 24.04 のイメージと、その機種が使えるアベイラビリティーゾーンを選ぶ。
3. キーペア、セキュリティグループ、cluster プレイスメントグループを作る。
   - セキュリティグループは、メンバー間の通信をすべて許可します（EFA に必須）。
   - SSH は、このマシンのパブリック IP からだけ許可します。
4. N 台を起動する（efa モードでは各台に EFA NIC を付けます）。
   - **各台は `--max-hours`（デフォルト 6 時間）に達すると自動でシャットダウンし、終了します。** 手元のマシンとの接続が切れても課金が続くことはありません。
5. 各台の環境を整え、ノード間で root のパスワードなしログインを設定する。
   - rxe：`rdma_rxe` を読み込み、`rdma link add rxe0` を実行し、MTU を 9001 にします。
   - efa：AWS の EFA インストーラー（libfabric を含む）を入れます。
6. コードツリーを 1 台目に転送し、そこで `./run.sh --peers <他の各台のプライベート IP>` を実行する。進捗はリアルタイムで表示されます。
   - 中身は、事前チェック、ビルド、転送の検証、機能テスト、ベンチマーク、全ノードの IO500 です。
7. レポートを `aws_runs/<run-id>/` に回収する。
8. インスタンスを終了し、作ったものをすべて削除する（`--keep` を付けると残します）。

| 引数 | 意味 |
|---|---|
| `--mode efa\|rxe` | 転送方式（デフォルト efa） |
| `--nodes` | 台数（デフォルト 10） |
| `--type` | インスタンスタイプ。デフォルトは efa が `c6in.32xlarge`（128 vCPU、200 Gb、RDMA read 対応の EFA）、rxe が `c6in.16xlarge`。ローカル NVMe が要るなら `i4i.32xlarge`。efa モードでは EFA 対応の機種が必須です（非対応ならその場で拒否し、起動しません） |
| `--quick` | 30 秒の短時間実行（付けなければ、短時間実行のあとに公式の 300 秒本番実行） |
| `--max-hours` | 安全上限（デフォルト 6） |
| `--keep` | 実行後も解放せず、ssh コマンドを表示 |
| `--self-test` | ヘッドノードでもユニットテストを実行 |
| `--az` / `--region` / `--ssh-cidr` / `--disk-gib` | アベイラビリティーゾーン、リージョン、SSH を許可するネットワーク範囲、システムディスク |

自分で起動済みの AWS マシンがある場合：

- **EFA 対応の機種**：EFA インストーラーを入れたあと、そのまま `sudo ./run.sh --peers ...`。EFA を自動で認識し、libfabric バックエンドを使います。
- **通常の機種**：`sudo ./run.sh --soft-roce --peers ...`。各台に rxe0 を自動で作ります。
- どちらも、セキュリティグループでメンバー間のすべての通信を許可しておく必要があります。

2 つの方法の違い：

- **rxe**：RDMA の操作をすべて CPU が行うので、帯域もレイテンシも実 NIC には遠く及びません。機能と複数ノードの流れの検証に向いています。
- **EFA**：本物の RDMA です（SRD 信頼性データグラム、Nitro v4 以上の機種はハードウェア RDMA read）。スコアに意味があります。
- EFA は順不同で配送するので、次のように扱います。
  - 片側読み込みの検証は順不同に合わせて行います（データを先に、バージョン番号をあとに読む）。
  - 片側メタデータ参照は、EFA ではデフォルトで無効です（3 往復かかり、RPC 1 回より遅いため）。`ROCEPOOL_DIRECT_LOOKUP=1` で強制的に有効にできます。

詳しくは `docs/AWS_ROUND.md` を参照してください。

## 4c. GPU 直接読み込み（GPUDirect Storage）

レンダリングや学習のように GPU を大量に使うプログラムは、rocepool から GPU メモリへ直接データを流し込めます。

- NIC が OST のメモリ上のデータを GPU メモリへ直接 RDMA で書き込みます。ホストメモリは経由せず、CPU はデータに触れません（WEKA や DDN の GDS 対応と同じです）。
- インターフェースは NVIDIA 標準の cuFile（`libcufile.so.0`）です。PyTorch/KvikIO、RAPIDS、DALI、cuFile でデータを読むレンダラーは、コードを変える必要がありません。

```bash
# GPU ノードで（build.sh で roce/native/cufile/libcufile.so.0 がビルド済み）
export LD_LIBRARY_PATH=<rocepool ディレクトリ>/roce/native/cufile:$LD_LIBRARY_PATH
export ROCEPOOL_MDTS=... ROCEPOOL_OSTS=...      # インターセプトライブラリと同じ
export ROCEPOOL_PREFIX=/mnt/rocepool            # FUSE のマウントポイント（またはインターセプトライブラリのプレフィックス）
python3 あなたのプログラム                       # その cuFile の読み書きが rocepool から GPU メモリへ直接流れる
```

- **手作業は何も要りません。** `run.sh` に `gds` ステップがあります（結果は `onsite_gds.json`、結果パッケージに含まれます）。
  - 各マシンについて次のことを確認します。
    - GPU とドライバー。
    - GPU メモリを NIC に登録できるか。dma-buf にはオープンソース版のカーネルモジュールが必要です。nvidia-peermem を使う方法もあり、こちらは足りなければ自動で modprobe します。
    - PCIe 上での GPU と NIC の距離。別の CPU ソケットにある場合は注意を表示します。
  - GPU があるマシンでは、速度も測定します。それぞれ GB/s で出します。
    - GPU メモリへ直接。
    - ホストメモリ経由。GDS 非対応のストレージはこうなります。
    - 全 GPU で同時に読み込み。
- GPU のないマシンでは、このステップは "no NVIDIA GPU" と表示され、失敗扱いにはなりません。
- GPU メモリを登録できない場合は、自動でホストメモリ経由に戻ります。結果は正しいままで、レポートに WARN が付きます。
- **AI 推論の KV キャッシュ（プレフィックスキャッシュ、prefill/decode の分離）**：KV API に、GPU メモリと直接やり取りする呼び出しを追加しました。KV ブロックに向いています。
  - Python での使い方：
    - `buf = kv.register_device(tensor.data_ptr(), バイト数)`
    - `kv.cached_prefix(ブロックキーのリスト)`：キャッシュ済みのプレフィックスのブロック数を、OST ごとに 1 往復で調べます。
    - `buf.mget(...)` / `buf.mput(...)`
  - データは NIC が直接 RDMA で GPU メモリに出し入れします。ホストメモリもメタデータサーバーも経由しません。
  - `run.sh` の `kvcache` ステップが自動で測定します。
    - 実際のモデルの KV サイズを使います。quick は Llama-3-8B で 4096 トークン中 3072 をキャッシュ、full は Llama-3-70B で 8192 トークン中 6144 をキャッシュします。
    - 保存、プレフィックス照会、GPU メモリへの読み込みを行い、ブロックごとにデータを検証します。
    - 出力：読み込みレイテンシ（p50/p99）、GB/s、TTFT。TTFT はキャッシュを使った場合とすべて再計算した場合を比べます。prefill の時間は GPU の型番の演算性能から見積もり、レポートにその旨を明記します。
    - 結果は `onsite_kvcache.json` です。GPU のないマシンでは「ホストメモリへの読み込み」の段だけを測ります。
- 詳しくは `docs/GPUDIRECT_STORAGE.md` を参照してください。

## 5. 結果の見方

実行が終わると表が 1 つ表示されます。全データは `io500_report.json` にあります。

```
phase            measured   emu%  rpc/op  hot MDT   projected   bottleneck
ior-easy-write   ...        ...                                 RAM to hold a 300 s write phase / NVMe tier write bandwidth
mdtest-hard-write ...                                           per-rank latency / CPU of the busiest node / ...
projected on ...: bw X GiB/s, md Y kIOPS, score Z
score range over the estimated inputs: a .. b
vs WEKA Afton (score 105.94): ...
what the fixes are worth (cumulative): ...
```

- **measured**：今回実際に出た数値です。実機ではこれがあなたのスコアです（本番実行では `[SCORE]` の行を見ます）。
- **bottleneck**：実測した操作あたりの CPU / RPC / バイト数から推定した、そのフェーズが最初に突き当たる上限です。
- **projected**：実測した 1 回あたりのコストを目標ハードウェアに当てはめた予測です（`--project`、実機のデフォルトは `auto` でそのホスト自身）。
  - 実機では実測と予測がほぼ一致するはずです。大きくずれる場合は、モデルが何かを見落としています。
  - 比率は表の "model check" の行に出ます。
- 実機のレポートでは、`node_facts`、`ost_tier`、`client_probe`、`fuse_channel_probe`、`dead_servers`（サーバーが落ちた場合はログの末尾付き）も確認する価値があります。

## 6. 手動での制御（任意）

`roce_onsite.py` でクラスターができあがったあと（`onsite_cluster.json`）は、`io500_run.py` を直接呼べます。

```bash
export ROCEPOOL_CLUSTER=onsite_cluster.json
sudo -E python3 tools/io500_run.py --valid                      # 公式の 300 秒本番実行
sudo -E python3 tools/io500_run.py --client intercept --ost-tier none   # インターセプトライブラリ + メモリのみを強制
sudo -E python3 tools/io500_run.py --ost-tier file:/dev/nvme1n1 # 各ノードの同じ生ディスク（上書きされます！）
sudo -E python3 tools/io500_run.py --ost-tier spdk:0000:41:00.0 # SPDK バックエンド（SPDK_DIR でのビルドが必要、下記参照）
```

よく使う引数：

| 引数 | 意味 |
|---|---|
| `--client auto\|fuse\|intercept` | 使うクライアント |
| `--direct-read auto\|on\|off` | 片側読み込みと片側参照。auto はプローブで有効と無効を比べて決める |
| `--bind-ranks auto\|numa\|core\|none` | ランクの割り当て方 |
| `--fuse-uring auto\|on\|off` | FUSE over io_uring |
| `--ost-tier auto\|none\|file:PATH[:GIB]\|spdk:TRADDR[:NSID]` | OST の容量層。`{n}` は OST の番号を表す |
| `--ost-ram-cache-mib` | OST の RAM キャッシュ |
| `--ranks-per-node`、`--mdts-per-node`、`--osts-per-node` | ノードあたりのランク数、MDT 数、OST 数 |
| `--stonewall`、`--valid`、`--project`、`--report` | stonewall 時間、本番実行、予測先、レポートのパス |

**SPDK バックエンド**の手順（各マシンで行います）：

1. SPDK をビルドします：`git clone https://github.com/spdk/spdk && cd spdk && git submodule update --init && ./configure && make`。
2. 対象の NVMe を vfio-pci にバインドします（`scripts/setup.sh`）。そのディスクはカーネルから切り離されます。
3. `SPDK_DIR=/path/to/spdk bash roce/native/build.sh` を実行します。
4. `--ost-tier spdk:<PCI アドレス>` を指定して実行します。

SPDK の経路は v25.05 のヘッダーでビルドが通ることを確認済みですが、ハードウェアではまだ動かしていません。初回は OST のログを確認してください。

**ローカルのベンチマークだけを実行する**（1 台。2 つのネットワーク名前空間、または実 NIC を使います）：

```bash
sudo python3 tools/bench_ior.py --backend dist --hard                      # FUSE クライアント
sudo python3 tools/bench_ior.py --backend dist --hard --client intercept   # インターセプトライブラリ
sudo python3 tools/io500_run.py --nodes 10                                 # このマシンで 10 ノードを一式シミュレーション
```

**インターセプトライブラリだけで任意のプログラムを動かす**：

```bash
LD_PRELOAD=roce/native/librocepool_intercept.so ROCEPOOL_PREFIX=/mnt/rocepool \
ROCEPOOL_MDTS=h1:19901,h2:19901 ROCEPOOL_OSTS=h1:19951,h2:19951 \
mpirun -n 32 ior -a POSIX -o /mnt/rocepool/f ...
```

`/mnt/rocepool` は存在しなくてかまいません。ただのプレフィックスで、それ以外のパスはそのまま libc に渡されます。

## 8. よくある問題

| 症状 | 対処 |
|---|---|
| 事前チェックの FAIL：RoCE モード / memlock | root での事前チェックが自動で修正します。修正できない場合は、具体的な sysfs/configfs のパスを表示します |
| ホスト名が同じ、または 127.x に解決される | スクリプトが自動で `/etc/hosts` を書いて修正します。それでも失敗する場合は、表示に従って手動で行を追加してください |
| "IO500 did not start in 300 s" | MPI のランク同士がつながっていません。ssh のパスワードなしログイン、ファイアウォール、ホスト名の解決を確認してください |
| サーバーが落ちた（`dead_servers`） | 該当する `ost<ノード>_<ポート>.log` / `mdt<ノード>_<ポート>.log` と、レポートの `kernel_log`（OOM など）を確認してください。メモリ不足なら `--mem-budget-gib` を見直してください |
| クライアントの RPC タイムアウト（`timed out waiting for completion`） | マシンがひどく過負荷のときに起きます。`ROCEPOOL_RPC_TIMEOUT_MS` を大きくしてください |
| OST のログに `ibv_reg_mr refused the supplied (P2P) chunk memory` | NIC のドライバーが P2P ページの登録に対応していません。自動でホストメモリに戻っているので、機能には影響ありません |
| `Write phase needed ...s instead of stonewall 300s`（ior-easy が INVALID） | データが 300 秒分に収まっていません。どの OST の容量で詰まったかは、実行冒頭の `IOR data budget ... from the OSTs' capacity` の行に書かれています。NVMe（LVM/RAID 上のものを含む）のファイルシステムは自動で層になります。ない場合は、このマシンで最大のローカルファイルシステムを使います。生ディスクには自動で書かないので、必要なら `--ost-tier file:/dev/nvmeXnY` を指定してください |
| 実行中にサーバーが落ちた | IO500 はすぐに止まり、残りのフェーズは実行しません。レポートの `dead_servers[].kernel_log` に、そのマシンのカーネルログ（OOM など）が付きます |
| NVMe 層への書き込み失敗 `tier full` | 層のファイルが小さすぎます。`--ost-tier file:PATH:GIB` で大きく指定してください |
| AWS：`has no EFA` | その機種は EFA 非対応です。`c6in.32xlarge` / `i4i.32xlarge` / `hpc7a.96xlarge` などに変えるか、`--mode rxe` を使ってください |
| AWS：事前チェックの `libfabric` が FAIL | EFA インストーラーが正しく入っていないか、セキュリティグループがメンバー間のすべての通信を許可していません |
| AWS：事前チェックの `rdma_read` が WARN | 機種が Nitro v4 以上ではありません。RDMA read は libfabric が相手側の CPU でエミュレートします。機能は正常ですが、片側読み込みは遅くなります。プローブが片側読み込みと RPC 読み込みのどちらかを自動で選びます |
| AWS：rxe が作れない | カーネルに `rdma_rxe` がありません。`apt install linux-modules-extra-$(uname -r)` を実行してください |
| AWS：途中で接続が切れた | マシンは `--max-hours` で自動終了します。`aws_cluster.py down --run-id ...` ですぐに解放することもできます |

## 9. 今回の結果のまとめ（詳しくは `docs/KERNEL_BYPASS_ROUND.md`）

- **インターセプトライブラリと FUSE の比較**（2 コアのエミュレーター、ior-hard）：インターセプトライブラリのほうが、書き込み 1.9 倍、読み込み 2.6 倍、create 1.5 倍。
- **10 ノードのシミュレーション**（`stress_reports/39`）：
  - 実測は 1.68 → 3.02。
  - 10 × 32 コア / 100 GbE への予測は 375（メモリのみ）/ 687（NVMe 層）。WEKA Afton は 105.94。
  - メタデータの予測は上限値で、帯域は実際のディスクの書き込み帯域で決まります。
- **同じハードウェア（96 コア / 750 GB / 200G）での予測**：806 / 1 342。項目別の比較は開発時のやり取りにあります。
- **片側読み込み・参照 + NUMA 固定**（`docs/ONE_SIDED_ROUND.md`、`stress_reports/41`）：
  - 10 ノードのシミュレーション実測は 3.02 → 3.77。
  - stat フェーズは 2.5〜3 倍、予測は 375 → 449。
- **AWS**（`docs/AWS_ROUND.md`）：
  - EFA 転送バックエンド（libfabric）を追加し、すべてのテストが両方のバックエンドで通りました。
  - `tools/aws_cluster.py` のコマンド 1 つでクラスターを起動して IO500 を実行できます。
